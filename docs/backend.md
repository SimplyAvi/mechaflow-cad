# Backend Development

MechaFlow CAD now has a first FastAPI backend scaffold under `backend/mechaflow_api`.

The backend is intentionally local-first and low-cost to host. It exposes project, reference design, assembly, part, material, task requirement, analysis readiness, analysis job queue, manufacturing, wiring, and report schemas before heavy CAD tools are fully wired in. It also includes a local pre-solver runner that packages readiness inputs into persisted review-required artifacts without running real FEA, plus a CalculiX solver-readiness fixture boundary that runs only when the local solver is installed. Job queue recommendations compare local readiness with cloud planning estimates, but no cloud provider, paid compute, billing, credential, or remote execution path is configured.

## Install dependencies

Use a virtual environment so backend dependencies stay isolated from other local projects.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e '.[dev]'
```

## Run tests

```bash
pytest
```

The test suite covers:

- Health and status endpoints.
- API metadata and schema exports for frontend mirroring.
- Seed catalog data.
- Core Pydantic schema validation.
- A local integration smoke test that starts the backend and the simple frontend shell on explicit free ports.

## Run the backend only

Choose a port explicitly when you want a stable URL:

```bash
export MECHAFLOW_API_HOST=127.0.0.1
export MECHAFLOW_API_PORT=8123
mechaflow-api
```

Then open:

```text
http://127.0.0.1:8123/api/docs
```

If `MECHAFLOW_API_PORT` is omitted, the backend defaults to port `0`, which asks the operating system to allocate an available port. This avoids reserving a fixed port, but you should set `MECHAFLOW_API_PORT` when another process, browser app, or frontend needs to know the URL.

If the configured port is busy, uvicorn exits with a clear bind error. Pick another port rather than silently colliding with another local project.

The backend allows the default Vite origins `http://127.0.0.1:5173` and `http://localhost:5173`. Add other local frontend origins explicitly as a comma-separated list:

```bash
export MECHAFLOW_CORS_ORIGINS=http://127.0.0.1:5179,http://localhost:5179
```

Include every frontend origin that should access the API. `python scripts/run-dev.py` configures its selected static-frontend origin automatically.

## Find an unused port

```bash
python scripts/find-free-port.py
```

Use the printed value as `MECHAFLOW_API_PORT` or `MECHAFLOW_FRONTEND_PORT`.

## Run backend and frontend together

The repository includes a tiny static integration shell in `frontend/` plus the product React cockpit in root `src/`. The static shell is useful for backend smoke coverage and catalog seed serving. Use the React cockpit for frontend product work; it connects to this backend with `VITE_API_BASE_URL` as described in `docs/frontend.md`.

```bash
python scripts/run-dev.py
```

By default the dev runner chooses available ports for both servers and prints the URLs. To choose explicit ports:

```bash
export MECHAFLOW_API_PORT=8123
export MECHAFLOW_FRONTEND_PORT=5179
python scripts/run-dev.py
```

The frontend receives the backend URL through `/runtime-config.js`, generated by the dev server at request time.

## Useful endpoints

- `GET /health` - process health.
- `GET /status` - service status plus integration adapter stubs.
- `GET /api/metadata` - product concepts, local development metadata, and adapter summaries.
- `GET /api/concepts` - concept names and descriptions.
- `GET /api/schemas` - JSON schemas for frontend and worker contracts.
- `GET /api/catalog/seed` - one payload with reference designs, materials, starter tasks, and the sample project for frontend bootstrapping.
- `GET /api/reference-designs` - seed reference design catalog entries.
- `GET /api/catalog/reference-designs` - committed catalog records and handoff metadata for the static integration shell.
- `GET /api/catalog/tasks` - committed task records used to label catalog handoff task IDs.
- `GET /api/materials` - starter material records.
- `GET /api/task-requirements/sample` - starter task requirements from seed reference designs.
- `GET /api/assemblies/sample` - sample parsed assembly shape.
- `GET /api/projects` - local in-memory project list seeded with the open gripper demo.
- `GET /api/projects/sample` - sample task-preserving project.
- `GET /api/projects/{project_id}` - fetch a local project by id.
- `GET /api/projects/{project_id}/export-file` - export a portable `.mfcad.json` project file envelope with project state, regenerated analysis readiness previews, and future CAD import extension slots.
- `POST /api/projects/import-file` - validate and import or reopen a portable MechaFlow project file. Malformed JSON, unsupported `format` or `schema_version`, and invalid project payloads fail with clear `4xx` errors without erasing current state.
- `POST /api/projects` - validate and create a local project, returning `409` for duplicate ids.
- `PUT /api/projects/{project_id}` - validate and upsert a local project using the path id as authoritative.
- `GET /api/projects/{project_id}/panel-data` - consolidated task, BOM, manufacturing, wiring, report, analysis-readiness, and job queue data for frontend panels.
- `GET /api/projects/{project_id}/task-requirements` - active task requirements for the project.
- `GET /api/projects/{project_id}/bom` - assembly-derived BOM rows with active manufacturing-option price and lead-time ranges when explicit seed data exists. These are estimates, not supplier quotes.
- `GET /api/projects/{project_id}/manufacturing-options` - part-grouped manufacturing options for the manufacturing panel.
- `GET /api/projects/{project_id}/parts/{part_id}/material-substitutions` - explicit compatible material and process substitutions for one selectable part. The list only includes process intersections supported by both the part and material.
- `POST /api/projects/{project_id}/material-substitutions/preview` - validate a requested material and manufacturing process, then return projected panel data and an advisory report without persisting the mutation.
- `POST /api/projects/{project_id}/material-substitutions/apply` - run the same validation and persist the substitution, invalidating regenerated readiness previews for the project.
- `GET /api/projects/{project_id}/electronics-components` - mounted PCB, sensor, connector, and cable-accessory records for electronics review.
- `GET /api/projects/{project_id}/wire-segments` - wire segment records with conductor count, AWG, length estimate, endpoints, and BOM linkage.
- `GET /api/projects/{project_id}/wiring-rules` - heuristic clearance, bend-radius, and service-loop thresholds used by the MVP review.
- `GET /api/projects/{project_id}/wiring-routes` - project wiring routes with connectors, path points, route metadata, and WireViz diagram references for the wiring panel.
- `GET /api/projects/{project_id}/wiring-electronics` - panel-ready wiring and electronics package with route review data and BOM context.
- `POST /api/projects/{project_id}/wiring-review` - deterministic MVP wiring review that reports `pass`, `warning`, or `review_required` with explicit evidence. It is a heuristic screen, not exact electrical or CAD validation.
- `GET /api/projects/{project_id}/reports` - generated advisory reports for the report panel.
- `GET /api/projects/{project_id}/analysis-readiness/{target_id}` - pre-solver readiness preview for a part or assembly, including explicit load cases, constraints, material provenance, thermal guidance, solver input placeholders, and expected FreeCAD, Gmsh, and CalculiX artifacts. This endpoint does not run FEA.
- `POST /api/projects/{project_id}/analysis-readiness/previews` - create the same local readiness preview from a target id without persisting a solver result.
- `POST /api/projects/{project_id}/analysis-jobs/pre-solver-runs` - create and synchronously run a local pre-solver screening job for a target. It persists a completed job with a `review_required_not_fea` artifact and reports FreeCAD, Gmsh, and CalculiX command availability.
- `GET /api/projects/{project_id}/analysis-job-queue` - return enriched queue rows with pending, running, completed, failed, review-required, and solver-unavailable states; local/cloud recommendation metadata; cost, runtime, and wait estimates; and cached report or artifact references.
- `GET /api/projects/{project_id}/analysis-jobs` - project-scoped enriched job rows for the same queue UI.
- `POST /api/projects/{project_id}/analysis-jobs/recommendation` - deterministic local vs cloud-planning recommendation for a proposed job. Cloud output is a planning estimate only and reports `cloud_execution_available: false` until provider configuration exists.
- `POST /api/projects/{project_id}/analysis-jobs/solver-readiness-runs` - create and synchronously run the CalculiX solver-readiness fixture boundary for a target context. If CalculiX is missing, it returns `solver_unavailable` with a generated `.inp` deck manifest and install guidance. If CalculiX is present, it invokes the deterministic fixture and collects logs and result files. The fixture is not project FEA.
- `POST /api/projects/{project_id}/modifications` - apply a local part-level edit, update material/dimensions/process metadata, and attach an advisory report.
- `GET /api/local-analysis/tool-boundaries` - inspect FreeCAD, Gmsh, and CalculiX command boundaries. Missing binaries return `unavailable_review_required` with install guidance instead of an unclear failure.
- `GET /api/local-analysis/solver-readiness` - summarize local pre-solver packaging, the executable CalculiX fixture mode, full-stack project FEA readiness, missing tools, and setup guidance.
- `GET /api/analysis-jobs` - in-memory local job list, optionally filtered by `project_id`.
- `POST /api/analysis-jobs` - queued orchestration metadata with stub adapter selection; `project_id` must name an existing project.
- `GET /api/analysis-jobs/{job_id}` - fetch a local in-memory job record.
- `GET /api/analysis-jobs/{job_id}/plan` - adapter plan showing queue name, expected artifact, and worker handoff notes.
- `POST /api/analysis-jobs/{job_id}/run-local` - run a queued `run_fea` or `quick_load_heuristic` job through the local pre-solver runner. This packages inputs only and does not invoke FreeCAD, Gmsh, or CalculiX.
- `POST /api/analysis-jobs/{job_id}/run-stub` - complete a local stub job and attach an advisory artifact without invoking heavy tools.

The project and job stores are intentionally in-memory for the local MVP. Restarting the API clears created projects and submitted jobs except for the seeded sample project. `backend/mechaflow_api/storage.py` defines the project repository boundary so a future persistence slice can move this contract to SQLite for local development and PostgreSQL for hosted use. Cached artifact file bundles follow the local retention rules in `backend/mechaflow_api/solver_execution.py`; stale or impossible download URLs are rejected on import instead of being treated as current results.

## Project file persistence

The MVP project file contract is documented in [Project files](project-files.md). The authoritative payload is the backend `Project` schema, so assemblies, parts, materials, electronics components, wire segments, wiring rule sets, wiring routes, active task requirements, modifications, analysis jobs, job recommendations, cached report references, cached artifact references, reports, and analysis job artifacts round-trip through the same validation used by normal project writes. Non-empty wiring route lists are validated against known parts, connectors, wire segments, electronics components, and rule sets so incomplete imports fail clearly instead of silently dropping harness data.

Export example:

```bash
curl -s http://127.0.0.1:8123/api/projects/project-open-gripper-demo/export-file \
  -o project-open-gripper-demo.mfcad.json
```

Import or reopen example:

```bash
curl -s -X POST http://127.0.0.1:8123/api/projects/import-file \
  -H 'Content-Type: application/json' \
  --data-binary @project-open-gripper-demo.mfcad.json | python -m json.tool
```

See [Project files](project-files.md) for the envelope fields, validation behavior, and future STEP and FreeCAD extension points.

## Material substitution and modification contracts

Material substitution is explicit and two-step:

1. `GET /api/projects/{project_id}/parts/{part_id}/material-substitutions` lists compatible choices by intersecting the selected part's manufacturing options with each material's `compatible_processes`.
2. `POST /api/projects/{project_id}/material-substitutions/preview` returns projected `ProjectPanelData` and an advisory report with `persisted: false`; it does not alter the stored project.
3. `POST /api/projects/{project_id}/material-substitutions/apply` runs the same validation and persists the material/process change with `persisted: true`.

Incompatible requests, unknown parts, unknown materials, blank ids, and missing explicit process compatibility return clear `4xx` errors and leave the in-memory project unchanged. Successful substitution responses include weight delta from density when possible, stiffness/yield/heat screening values, process cost and lead-time ranges, warnings, and review-required labels. These values are seed estimates and are not FEA, CAD mass properties, or supplier quotes.

The lower-level `POST /api/projects/{project_id}/modifications` endpoint remains available for local part edits. `backend/mechaflow_api/services.py` updates the selected part, returns a `requires_review` report, and derives BOM, manufacturing, wiring, task, and report panel payloads so frontend flows can be built before FreeCAD, FEA, wiring, and supplier workers produce authoritative artifacts.

Modification requests accept positive, finite changes to `length_mm`, `width_mm`, `height_mm`, and
`thickness_mm`. A material change, or any request that supplies a manufacturing process, must resolve to a
process supported by both the selected part and material. Effective material or dimension changes clear the
stored part mass until a CAD worker recalculates it; resubmitting existing values preserves the mass and
reports that no corresponding change occurred. Readiness cache invalidation is tied to persisted project writes, not non-persisted previews.

## Analysis readiness contract

Analysis readiness previews are pre-solver artifacts. They record what a future solver worker needs and what still requires review:

The API accepts either a part or an assembly target. Assembly previews aggregate every included part, require complete aggregate geometry, dimensions, and material inputs before reporting `pre_solver_ready`, and remain review-required when those inputs are missing or mixed. Aggregate previews do not invent part-level demo estimates.

- Load cases with magnitude, unit, direction, application region, and confidence.
- Constraints with fixture or fastener regions and constrained degrees of freedom.
- Material property sets with provenance and seeded-property confidence.
- Heat-deflection or service-temperature guidance for thermal screening.
- Solver input placeholders for geometry source, mesh sizing, FreeCAD documents, Gmsh models, and CalculiX decks.
- Expected artifacts for FreeCAD geometry prep, Gmsh mesh, CalculiX input and result files, and a report JSON.

These previews are not FEA results. Any seeded capacity is labeled as a demo estimate and remains review-required until a real solver and engineering review replace it.

## Analysis job queue and recommendations

`backend/mechaflow_api/job_queue.py` enriches every analysis job with an explainable execution recommendation. The deterministic policy is conservative:

- Local pre-solver packaging is recommended for review artifacts because it does not invoke CAD, meshing, solver, cloud, or paid services.
- The CalculiX fixture remains local-only. If `ccx` is missing, the job is `solver_unavailable` or review-required and can still cache the generated input deck manifest.
- Full project `run_fea` requires readiness inputs plus FreeCAD, Gmsh, and CalculiX. Missing tools, missing CAD, missing material data, missing load cases, or review-required fixtures block execution rather than pretending a solve is available.
- High complexity, missing local tools, or a non-local preference can produce `cloud_recommended_when_configured`, but this is only a planning recommendation. Cost and wait values are labeled as planning estimates, not billing, quotes, or provider prices.

Use this endpoint to inspect queue behavior:

```bash
curl -s http://127.0.0.1:8123/api/projects/project-open-gripper-demo/analysis-job-queue | python -m json.tool
```

Use this endpoint to preview a proposed job recommendation without creating a job:

```bash
curl -s -X POST http://127.0.0.1:8123/api/projects/project-open-gripper-demo/analysis-jobs/recommendation \
  -H 'Content-Type: application/json' \
  -d '{"job_type":"generate_exploded_view","target_id":"asm-open-gripper-demo","project_id":"project-open-gripper-demo"}' | python -m json.tool
```

## Local pre-solver runner and solver-readiness fixture

The local runner in `backend/mechaflow_api/runners.py` gives the desktop demo an end-to-end pre-solver job path while staying honest about scope. It:

- Creates queued and running job states, then persists a completed or failed job update in the in-memory project store.
- Packages the selected target's readiness load cases, constraints, material provenance, solver inputs, and expected artifacts.
- Computes a deterministic nominal section screening estimate only when force, dimensions, and material strength are available. The artifact labels this as `demo_pre_solver_not_fea` and `review_required_not_fea`.
- Checks command boundaries for FreeCAD (`freecadcmd`, `freecad`, `FreeCAD`), Gmsh (`gmsh`), and CalculiX (`ccx`, `calculix`) with `shutil.which`. It does not invoke them. Missing binaries are reported as `unavailable_review_required` in job artifacts and through `GET /api/local-analysis/tool-boundaries`.

The executable boundary in `backend/mechaflow_api/solver_execution.py` adds a deterministic CalculiX fixture path. It generates a small `.inp` deck, records the file manifest, and runs `ccx mechaflow_static_fixture` only when CalculiX is found on `PATH`. A successful fixture is real solver execution, but it proves solver plumbing only. It does not analyze the selected project part or assembly, because FreeCAD geometry prep and Gmsh meshing for project geometry are still future workers.

Example:

```bash
curl -s -X POST http://127.0.0.1:8123/api/projects/project-open-gripper-demo/analysis-jobs/pre-solver-runs \
  -H 'Content-Type: application/json' \
  -d '{"target_id":"part-finger-link"}' | python -m json.tool
```

A successful response means the pre-solver package was generated. It does not mean a mesh or solver result exists.

## Integration stubs

The API does not import FreeCAD, CalculiX, Gmsh, KiCad, WireViz, or supplier SDKs in-process. Instead, `backend/mechaflow_api/adapters.py` defines capability metadata, queue names, job planning, and stub artifact generation boundaries for future workers:

- `freecad-worker`
- `local-pre-solver-runner`
- `freecad-fea-prep-worker`
- `gmsh-meshing-worker`
- `calculix-fea-worker`
- `kicad-electronics-worker`
- `wireviz-harness-worker`
- `supplier-options-worker`

This keeps local setup cheap while preserving clean integration seams for real CAD, FEA, electronics, wiring, and supplier work.
